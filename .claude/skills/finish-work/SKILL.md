# Finish work

For changed source/comments/Doc, examples, configuration/schema or instructions, assess [comment/Doc](../../../docs/development/comment-doc.md) against the actual diff and affected contracts, explanations/tests/references and protected evidence. Preserve necessary why/non-obvious how and source/artifact identity; link syntax alone is not semantic conformity or completed application to existing code.

Use the [GitHub workflow](../../../docs/development/github-workflow.md) for validation/progression and [PR automation](../../../docs/development/pr-automation.md) for handoff. A review-only request returns the fixed-diff/acceptance assessment; do not perform writer/coordinator operations.

**Verifiable result:** Run `python3 scripts/workflow/change_impact.py --run-tests` on the fixed Issue diff; record selected checks and skip reasons. Explicit packaging/GUI builds also require `buildPlugin`. Do not expand successful validation of an unchanged diff without a reason; changes, failures or unresolved concerns justify relevant checks. Preserve required CI/hooks, fix relevant failures and push only the owned branch.

**Independent assessment:** A separate top-level session meeting the [role/model policy](../../../docs/development/github-workflow.md#正本と役割) reviews HEAD/base and Issue acceptance, distinguishing scope_complete, issue_complete and GUI need. Unresolved code findings or required-test failures block both targets. Additional sessions follow the [Codex execution policy](../../../docs/development/codex-execution-policy.md). Do not equate Mission/ACP First policy with implementation/live success. For development-context creation, updates, review or audit, apply the [single context policy](../../../docs/architecture/knowledge.md#開発コンテキストの用途言語形式と読込条件): trace old requirements, loading routes and justified evidence/language exceptions. Report static checks, actual client/model behavior and resource measurements separately.

**Handoff:** Stop the writer and confirm clean state before trusted-main v2 enrollment. The coordinator then manages implementation-worker fixes, independent re-review, four required checks and guarded merge; a PM does not edit source fixes or perform independent review. Reconcile model readback and uncollected results, then reassess finite capacity and the next assignment at each transition. PM verifies actual execution; if stopped, record the next owner and concrete blocker. Registration does not prove progress. Preserve existing owner/source and PAUSED heartbeat. Limit the #83 bootstrap exception to its documented procedure.

**Integration and closure:** Develop can squash with all Cases tracked, retaining GUI pending/blocked/fail (product failures need fix Issues). Transfer remaining Cases to QA with bidirectional readback. Do not create QA when there are no Cases: retain explicit PM main-reflection custody and the next candidate/promotion readback in the existing Issue/PR. Reconcile existing QA rather than automatically closing or reclassifying it. Close implementation scope only after its acceptance and actual handoff are complete. Freeze known corrections and necessary operations sync into one combined candidate before final acceptance. Main promotion covers every candidate commit/required Case by current observations or explicitly certified evidence reuse under [verification](../../../docs/verification/README.md), followed by merge commit. Preserve original failures, identities and explicit execution obligations. Do not substitute old partial passes or changes beyond permitted promotion JSON. Never close tracking/research parents or QA merely because a child PR merged.

**Remaining work:** Follow [Work Management](../../../docs/development/work-management.md) to read back origin/QA Project, Milestone, native relationships and human instructions. Use `--parent` only for a real parent. Clean up only owned, stopped, clean resources; verify remote/local/tracking refs and worktrees are gone, or record retention reason/owner/resumption condition. Never delete main/master/develop; preserve GUI lease, unsaved work and existing owners. Merge success alone is not completion.

Apply [product responsibility](../../../docs/verification/responsibility.md) and the [ready worker brief](../../../docs/development/team-worker-prompt.md): guarantee → qualified existing evidence → missing fact → minimum sufficient method. Separate complete data/production regression from representative native glue; no missing fact means no new execution. Reuse needs fixed provenance, relevant unchanged/equivalent conditions, current load facts and independent substantive assessment. A method revision is not new execution or PASS. Do not repeat all native operations just because a ZIP or document changed. Use the conditional [Android Studio knowledge route](../../../docs/development/android-studio.md), without mandatory foreign-repository surveys.

Use [risk-managed continuation](../../../docs/development/github-workflow.md#公開操作の承認範囲と失敗の扱い). Before stopping unfinished work apply [stop reconsideration](../../../docs/development/omil-portable.md#reconsider-before-stopping-unfinished-work); obey human pauses and actual permission/safety/resource limits first. Keep cause, preserved/unmet state, residual owner and concrete resume conditions. Team roles and liaison are event-driven under [communication](../../../docs/development/team-communication.md), with no idle jobs or routine new approvals. PM receives substantive results; the writer, independent reviewer and actual integrator own detailed evidence checks, with PM investigating concrete exceptions.

For new Issues/branches/commits/PRs, use [work-management naming and metadata](../../../docs/development/work-management.md#命名); retain legacy read compatibility and preserve historical refs/titles. Use the guarded exact own-repository URL route for Project #2 changes once adopted. CI/input changes follow [CI impact](../../../docs/development/ci.md): preserve meaningful required checks and fixed inputs; use normal results or justified reuse/omission instead of duplicate benchmarks.

For original acceptance-NG corrections, classify Acceptance repair in the Issue and follow verification’s preserved failure/corrected candidate/full failed-guarantee/independent assessment gate. The ordinary pending-GUI exception cannot waive this. Preserve runtime origin and private original evidence; no alias or related unit PASS substitutes for the actual assessment.
