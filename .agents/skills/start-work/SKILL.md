# Start work

Read-only advice/review needs no new Issue or branch. For changes, use AGENTS.md and the [workflow's conditional references and decisions](../../../docs/development/github-workflow.md#参照する範囲と進行判断). Reuse already-read unchanged versions. New features need Mission/ACP First, product changes need relevant requirements/design, and operational changes need the corresponding policy. Creating/updating development context also requires the [single context policy](../../../docs/architecture/knowledge.md#開発コンテキストの用途言語形式と読込条件); classify purpose and loading path before choosing language/format/location.

Before a new or resumed assignment, apply the [role/model and finite-team policy](../../../docs/development/github-workflow.md#正本と役割): reconcile existing owners, execution handles and uncollected results; verify actual model/effort and role independence. Reuse eligible existing sessions before adding one; unknown/unavailable settings stop that assignment, not independent work.

Start when the Issue/comments, related PRs, Project/relevant Milestone, dependencies and acceptance are understood and no writer conflicts exist. Search before creating an Issue. Claim owner, scope, base SHA, dependencies, independent reviewer, GUI need and next action; read back the claim. Unreleased claims never expire with time. Follow [Work Management](../../../docs/development/work-management.md) for Project/labels/native relationships; never invent a parent for Standalone work.

Inspect status/worktrees, fetch with `git fetch --no-prune origin`, and reconcile the base of the dedicated Issue branch/worktree. Normally use origin/develop; GUI-not-required main tooling follows the workflow conditions. Clear initial upstream and run `bash scripts/workflow/bootstrap.sh`. On resumption first reconcile owner/source/execution handles. The same owner reuses the existing worktree; do not recreate it before checking. For takeover, follow [interruption/resumption](../../../docs/development/github-workflow.md#中断再開): confirm the old writer stopped and the claim was released or explicitly reassigned, then make the new claim and use the new owner's dedicated worktree. Never share the old owner's directory. Do not edit enrolled branches concurrently or automatically change owner/source; follow [PR automation](../../../docs/development/pr-automation.md).

Record all acceptance Cases in `docs/verification/changes/issue-N.json`: Japanese steps/expectations, agent/human state (legacy `gpt`/`human` keys) and fix/recheck tracking. If GUI is unnecessary, record why and the required CLI checks. Create a Draft PR with Integration/Verification on the first meaningful push, then continue implementation/validation. GUI requires the designated operator/lease; never mark unobserved behavior pass.

Start procedures or an initial PR are not completion. Continue to acceptance and [finish-work](../finish-work/SKILL.md). Before additional sessions/independent review, read the [Codex execution policy](../../../docs/development/codex-execution-policy.md).

Apply [product responsibility](../../../docs/verification/responsibility.md) and the [ready worker brief](../../../docs/development/team-worker-prompt.md): guarantee → qualified existing evidence → missing fact → minimum sufficient method. Separate complete data/production regression from representative native glue; no missing fact means no new execution. Reuse needs fixed provenance, relevant unchanged/equivalent conditions, current load facts and independent substantive assessment. A method revision is not new execution or PASS. Do not repeat all native operations just because a ZIP or document changed. Use the conditional [Android Studio knowledge route](../../../docs/development/android-studio.md), without mandatory foreign-repository surveys.

Use [risk-managed continuation](../../../docs/development/github-workflow.md#公開操作の承認範囲と失敗の扱い). Before stopping unfinished work apply [stop reconsideration](../../../docs/development/omil-portable.md#reconsider-before-stopping-unfinished-work); obey human pauses and actual permission/safety/resource limits first. Keep cause, preserved/unmet state, residual owner and concrete resume conditions. Team roles and liaison are event-driven under [communication](../../../docs/development/team-communication.md), with no idle jobs or routine new approvals. PM receives substantive results; the writer, independent reviewer and actual integrator own detailed evidence checks, with PM investigating concrete exceptions.

For new Issues/branches/commits/PRs, use [work-management naming and metadata](../../../docs/development/work-management.md#命名); retain legacy read compatibility and preserve historical refs/titles. Use the guarded exact own-repository URL route for Project #2 changes once adopted. CI/input changes follow [CI impact](../../../docs/development/ci.md): preserve meaningful required checks and fixed inputs; use normal results or justified reuse/omission instead of duplicate benchmarks.

For original acceptance-NG corrections, classify Acceptance repair in the Issue and follow verification’s preserved failure/corrected candidate/full failed-guarantee/independent assessment gate. The ordinary pending-GUI exception cannot waive this. Preserve runtime origin and private original evidence; no alias or related unit PASS substitutes for the actual assessment.
